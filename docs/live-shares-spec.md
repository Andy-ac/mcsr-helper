## 0. 一句话结论

新增一个顶级栏目「**实时分享**」，让**已登录用户**短暂地把「私人房房间号」或「一组世界种子」挂在一块公共看板上，
每条自己带一个 5 / 10 / 15 / 20 分钟的展示窗口，到点自己消失，作者随时可下架（可恢复）。

| 项 | 值 |
|---|---|
| 新表 | `live_shares`（迁移 **019**，纯 `CREATE TABLE` + `CREATE INDEX`，不改写任何既有数据） |
| 新能力 | **1 个**：`share.moderate`（进 `EDITOR_CAPS` ⇒ editor / admin / owner） |
| 新端点 | **4 个**（1 读 + 1 摘要 + 1 写 + 1 下架恢复） |
| 新路由 | **3 个**：`/shares`（公开介绍页）、`/shares/room`、`/shares/seed` |
| 新前端文件 | 3 个（介绍页、看板页、分享卡片组件）+ 一个新渲染自检脚本 |
| 全站影响 | ⚠️ **本栏目是第一个"内容游客看不到"的地方**（见 §1.1） |

**一句话概括数据模型**：一张表 + `kind` + 类型化 JSON payload，**加第三个标签页不需要迁移**。

## 1. 用户原话与逐条落地

> 「新增一个大栏目"实时分享"，分享私人房代码/暂时记录种子"，允许已登录普通用户短暂记录并向其他已登录用户
> 展示一些信息，顶部暂时分成两个栏目，"私人房"和"种子"。"私人房"栏目允许用户输入一段字母或数字，
> 并配上一段简短的说明（<20字/40字符），并且允许设置展示时间（5分钟一档，最多20分钟），拥有者可以随时下架；
> "种子"栏目允许用户输入三个世界种子和一个RNG种子，并配上一段简短的说明（<50字/100字符），
> 并且允许设置展示时间（5分钟一档，最多20分钟），拥有者可以随时下架。」

| # | 要求 | 落地 |
|---|---|---|
| ① | 新顶级栏目「实时分享」 | `NAV_SECTIONS` 新增一行（放在「直播」之后、「排位赛种子」之前），`block` 短名 `shares` |
| ② | 分享私人房代码 / 暂时记录种子 | 两个 `kind`：`room` / `seed`，同一张表、同一套机制 |
| ③ | 已登录用户**短暂**记录 | 发布要求 **登录 + 邮箱已验证**；展示窗口 5–20 分钟，到点即从列表消失 |

| ⑤ | 顶部两个栏目 | `/shares/room`、`/shares/seed` 两个标签页；`/shares` 是**公开的介绍页**（不是跳转） |
| ⑥ | 房间号：一段字母或数字 | 字符集 `A–Z a–z 0–9 - _`，长度 3–20，**原样保存原样显示**（不折叠大小写） |

| ⑩ | 展示时间 5 分钟一档、最多 20 分钟 | 四档 **5 / 10 / 15 / 20**，服务端只接受这四个值；**默认 5** |
| ⑪ | 拥有者可以随时下架 | `PATCH .../visibility { visible:false }`，**可恢复**（只要还没到点） |

### 1.1 ⚠️ 本栏目打破了全站的一条基础约定，这一条必须留在文档里

本仓的访问模型在 `docs/progress.md` 与 `docs/v1-plan.md` §0.1 都写着：**「浏览不需要登录；登录只是为了参与。游客能看完整站内容。」**
连资源库的只读版本当年都是特意做成"不依赖用户系统"的。

**「实时分享」的第一个内容面（两个看板）是第一个游客看不到的东西。** 这是用户的明确要求（「向其他已登录用户展示」），
不是疏忽。⇒ 后果有两条，都要认下来：

1. **「游客能看完整站」这句话从今往后不再成立。** 以后每加一个栏目，都要单独回答"这一栏给不给游客看"，
   不能再默认"给了"。
2. **介绍页刻意做成公开的**，作为这条线的一处缓冲：游客仍然能知道这个栏目是干什么的、为什么他看不到内容。
   ⇒ 游客不是撞上一堵墙，而是读到一句解释。

## 2. 已裁决的口径（**权威**，不再是待答清单）

| # | 问题 | 裁决 | 理由（用户拍板时的依据） |
|---|---|---|---|
| 1 | 到点 / 下架之后，数据怎么处理 | **到点什么都不做**（只是查询条件不再成立）；**下架 = 可恢复**；行留 **24 小时**再由定时任务回收 | ① 过期不靠任务才正确 ⇒ 没有"回收没跑、过期内容还挂着"这个故障模式；② 下架可逆，与上一轮"贡献者不实际删除"同形 |
| 2 | 同时能挂几条 | **一人一页一条**（room）；再发 = **替换**（旧行置 `replaced`） | 20 分钟的内容天生是"当前状态"型，不是"积累"型；一人两行对看的人是噪音 |
| 3 | 房间号与种子的格式 | 房间号 `[A-Za-z0-9_-]` 3–20；种子非空、≤32 字符、**不含空白** | **两种错的代价不对称**：收严了合法输入被挡在外面且没人会替你报上来；收松了最坏只是"有人贴了一个别人点不进去的码"，而它 20 分钟后自己消失 |
| 4 | 谁可以发 | **登录 + 邮箱已验证**；**不加额外限流** | 用户明确选择。⚠️ 限流的替代方案被否决：一个账号在 room 页最多占一行，"刷屏"已经被结构消掉了；真要刷只能多注册账号，而那是**全站**的问题，单独让这一栏扛的结果是"用的人被罚、想刷的人多注册一次就绕过" |
| 5 | 数据怎么存 | **一张表 + `kind` + 类型化 JSON payload** | 「顶部**暂时**分成两个栏目」⇒ "加第三个标签页要付什么"是首要判据；本方案**不需要迁移**（vs 两张表 = 信封写两遍；vs 平铺列 = 一次迁移） |
| 6 | `/shares` 是什么 | **公开的介绍页**（不是跳转），两块入口卡片，点进去才是看板 | 用户要求；同时它把 §1.1 那条断裂变成"读一句解释"而不是"撞一堵墙" |
| 7 | 「说明」必填吗 | **选填**（两个 kind 都是） | 用户裁决 |
| 8 | 展示时长默认值 | **5 分钟**（第一档） | 用户裁决 |
| 9 | 看板要不要自动刷新 | **要**，每 **20 秒**一次；页面不可见时停 | 一栏叫「实时分享」的东西，不自动刷新等于"别人刚发的你永远看不到" |
| 10 | seed 额度满（20）之后 | **拒绝**（409 `at_limit`） | 与裁决 2 同一条原则：**覆盖必须是本人明确按下去的动作**；顶掉最旧那条是"你没按、但东西没了" |
| 11 | 管理员能不能下架别人的 | **能**，新增能力 `share.moderate`（editor 及以上）；**但恢复只有本人能做** | 这一栏没有审核，管理员下架是**唯一**的兜底；管理动作应当是单向的 —— "放回去"要么是作者的判断，要么不该由第三方代劳 |
| 12 | 房间号第二格是不是"换一条" | room 是替换（一节一条）；**seed 是"再加一条"**（最多 20 条同时） | 用户裁决（room 1 条 / seed 20 条） |

### 2.1 被否决的替代方案（记下来，免得下次重新讨论一遍）

| 方案 | 为什么否决 |
|---|---|
| 两张独立的表（`live_share_rooms` / `live_share_seeds`） | 「信封」（谁发的 / 说明 / 到期 / 下架 / 回收 / 一人一条）要写两遍，而它恰恰是最容易两边漂移的部分；加第三个标签页要再来一套表与路由 |
| 一张表、字段平铺成列（`room_code` / `seed_overworld` / … 可空 + CHECK） | 两个 kind 的字段**零重叠**，每读一处都要先想"这一列在这个 kind 下有没有意义"；加第三个标签页要一次迁移 |
| 把「seed 最多 20 条」写进 schema（`slot` 列 + `CHECK(slot BETWEEN 0 AND 19)`） | 能强制，但**以后把 20 改成 30 就需要一次迁移**（SQLite 改 CHECK 必须重建表）—— 而"以后加东西不用迁移"正是选 JSON payload 的全部理由。⇒ 语义不变量进库，**额度进数据层**（参见 §3.3） |
| 到点靠定时任务删行 | 任务没跑/跑挂 ⇒ 过期内容继续挂在看板上，而界面上一切正常。⇒ 到点必须是**查询条件**，任务只管回收体积 |
| 靠客户端时钟算剩余时间 | 谁的电脑快 3 分钟，还没到点的行就被他提前抹掉；慢 3 分钟则过期的行一直挂着。⇒ 服务端下发 `serverNow`（§5.1） |
| 给 room 也做"到 20 条顶掉最旧" | 见裁决 10 |
| 不做介绍页，`/shares` 直接跳到 `/shares/room` | 用户否决；且会让游客撞上一堵没有解释的墙 |

## 3. 数据模型（冻结）

### 3.1 迁移 019

⚠️ **019 这个编号在 2026-09-15 现读过 `services/api/src/db/migrate.ts` 确认**：当前最新是
`018_content_contributors`，所以下一个是 019。动手时若已有别人插进来的迁移，往后顺延 ——
**已经发布的迁移一个字都不能改**（那个文件自己写着这条）。

```sql
CREATE TABLE live_shares (
  id          TEXT    PRIMARY KEY,
  user_id     TEXT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  kind        TEXT    NOT NULL CHECK (kind IN ('room','seed')),
  payload     TEXT    NOT NULL,                    -- JSON，形状由 kind 决定
  note        TEXT    NOT NULL DEFAULT '',         -- 选填 ⇒ 空串（不是 NULL）
  status      TEXT    NOT NULL CHECK (status IN ('active','hidden','replaced')),
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL,
  hidden_at   INTEGER,                             -- 只有 hidden 时有值
  CHECK (expires_at > created_at),
  CHECK ((status = 'hidden') = (hidden_at IS NOT NULL))
);

-- ★ 语义不变量：一个人同时只能有一条「私人房」在展示
CREATE UNIQUE INDEX idx_live_shares_room_one
  ON live_shares(user_id) WHERE kind = 'room' AND status = 'active';

-- 看板查询（按 kind + 有效期）
CREATE INDEX idx_live_shares_board  ON live_shares(kind, expires_at);
-- 「我的那些」查询 + 额度计数
CREATE INDEX idx_live_shares_user   ON live_shares(user_id, kind, status);
-- 回收任务
CREATE INDEX idx_live_shares_sweep  ON live_shares(expires_at);
```

**两条 CHECK 是刻意加的**（都是"把不可能的状态变成插不进去的行"）：

- `expires_at > created_at`：展示窗口永远是正数。
- `(status = 'hidden') = (hidden_at IS NOT NULL)`：**`hidden_at` 与 `hidden` 状态必须同时出现或同时缺席**。
  没有这一条，"已下架但不知道什么时候下架的"和"没下架却带着下架时间"两种行都能写进去，而它们在审计里看起来都正常。

### 3.2 payload 的两种形状（冻结）

```jsonc
// kind = 'room'
{ "code": "A7K2P" }

// kind = 'seed'          —— 除 overworld 外都可能缺席（缺席 = 这个键不存在，不是空串）
{ "overworld": "1234567890123456789",
  "nether": "...", "end": "...", "rng": "..." }
```

- ⚠️ **读出来时也要过一遍 zod**（与写入同一份 schema）。理由：payload 只有应用层知道形状，
  一次手改库、一次回滚、一次将来的迁移都可能留下"形状对不上 kind"的行 ⇒ 必须**跳过并记日志**，
  **不是**把它透传给前端（前端拿到半个形状只会渲染出破折号，看起来像我们这个功能坏了）。
  有一条测试专门喂这种行。
- ⚠️ 空字符串**不存**：种子的选填格 trim 之后为空 ⇒ 该键**不存在**。所以"填了没有"与"填了空"在库里是同一件事，
  前端不需要判断两种空。

### 3.2.1 「20字/40字符」到底怎么算 —— 冻结成一张区间表

用户给的是「＜20字/40字符」（种子是「＜50字/100字符」）。**唯一自洽的读法是"显示宽度预算"**：
一个汉字占两个半角位，所以「20 字」与「40 字符」是**同一个预算的两种说法**。纯中文或纯英文时两种读法一致，
**只有中英混写时不同** —— 而混写是常态（`1.16 RSG 三缺一`）。

⇒ 冻结的算法（**不要用 `String.length`**，它数的是 UTF-16 单元，会把 emoji 数成 2 并在代理对上出错）：

1. 先把字符串按 **码点**（`[...str]`）拆开；
2. 每个码点算 `2` 当且仅当它落在下表任一区间，否则算 `1`；
3. 求和，与该 kind 的预算（room **40** / seed **100**）比较。

| 区间 | 是什么 |
|---|---|
| `U+1100–U+115F` | 谚文字母 |
| `U+2E80–U+303E` | 中日韩部首与符号 |
| `U+3041–U+33FF` | 假名、注音、中日韩兼容 |
| `U+3400–U+4DBF`、`U+4E00–U+9FFF` | 中日韩统一表意文字（含扩展 A） |
| `U+A000–U+A4CF` | 彝文 |
| `U+AC00–U+D7A3` | 谚文音节 |
| `U+F900–U+FAFF` | 兼容表意文字 |
| `U+FE30–U+FE4F` | 中日韩兼容形式 |
| `U+FF00–U+FF60` | 全角形式 |
| `U+FFE0–U+FFE6` | 全角符号（￥ ￦ 等） |
| `U+1F300–U+1FAFF` | emoji |

⇒ 后果（都要写进测试）：`A7K2P` = 5；`1.16 RSG 三缺一` = 11 + 6 = **17**；**20 个汉字 = 40 ✓**、**21 个汉字 = 42 ✗**；
一个 emoji 算 2（与一个汉字同宽，符合直觉）。

### 3.3 两种限额，落在两个地方（**刻意不对称**）

| | 性质 | 落在哪 | 怎么保证 |
|---|---|---|---|
| room **1** 条 | **语义不变量** | **数据库**（上表那个部分唯一索引） | 数据库报错，不是靠代码自觉 |
| seed **20** 条 | **额度**（防灌水的数字，将来会调） | **数据层**（写入事务里数一遍） | 一条测试钉着：第 21 条必须 409 |

**为什么数据层那个是安全的**（这不是"没做数据库约束"的借口，是一条依据）：
`POST` 的"数一遍"与"插进去"在**同一个事务**里，而这个服务是**单进程 + 同步 SQLite 驱动**（`node:sqlite`），
所以两者之间**不可能**插进另一个请求。本仓的 `setContributors`（注释原文：「存在性检查必须与写入**同一个事务**」）
用的就是这同一条依据。测试里会**并发**发两条（19 条时），断言恰好一条成功。

### 3.4 ⚠️ 一个必须写下来的交互：过期的 room 行仍然占着那个唯一索引

部分唯一索引的谓词是 `kind='room' AND status='active'` —— **它不看过期**。所以：

- 我上一条房间号 1 分钟前到点了，但回收任务还没跑（它每小时跑一次）⇒ 库里仍有一行 `active` 的 room 行；
- 此时我发一条新的：`POST` 的事务**第一步就是把我自己所有 `active` 的 room 行置为 `replaced`**，
  再插新行 ⇒ 索引条件自然满足。

⇒ **替换这一步不是"顺手清理"，它是让索引能成立的必需步骤。** 若将来有人把"先置 replaced 再插入"改成
"先查有没有、有就报错"，这个索引会立刻开始拒绝**正常**的发布。
有一条测试专门覆盖它：**上一条已过期但未被回收时，仍然发得出新的**。

## 4. 状态机（冻结）

### 4.1 「在不在看板上」只有一个判据，而且只有一处实现

```
status = 'active' AND expires_at > now
```

| 原因 | 库里怎么变 | 还能回来吗 |
|---|---|---|
| **到点** | ⚠️ **什么都不做** —— 不是一次状态变更，只是上面那个条件不再成立 | 不能 |
| **拥有者下架** | `active → hidden`（写 `hidden_at`） | **能**，只要 `expires_at > now` |
| **管理员下架** | 同上（审计的 `reason` 里写明是管理员） | 能，**但只有拥有者本人**能恢复 |
| **被新发布替换**（只可能发生在 room） | `active → replaced` | 不能（它就是被换掉的那条） |
| **回收任务** | 物理删除（`expires_at < now - 24h`） | 不能 |

### 4.2 状态迁移的合法性（服务端必须拒绝的）

| 请求 | 行的当前状态 | 结果 |
|---|---|---|
| 下架（本人或管理员） | `active` | 200，`active → hidden` |
| 下架 | `hidden` / `replaced` | **409 `invalid_state`**（已经是隐藏的，再下架一次没有意义） |
| 下架 | `active` 但**已过期** | **409 `invalid_state`，reason `expired`** |
| 恢复（**只有本人**） | `hidden` 且未过期 | 200，`hidden → active` |
| 恢复 | `hidden` 但**已过期** | **409 `invalid_state`，reason `expired`** |
| 恢复 | `replaced` | **409 `invalid_state`** |
| 恢复 | 管理员对**别人**的行 | **403**（管理员的下架是单向的，见裁决 11） |
| 恢复 | room：本人**已经有另一条 active 的 room** | **409 `at_limit`** + 「你已经在展示另一条了，先把它下架再恢复这条」（见 §4.3） |
| 恢复 | seed：本人已满 20 条 active | **409 `at_limit`** |

### 4.3 ⚠️ 为什么"恢复 room"要先看额度，而不是自动顶掉那条

场景：我挂了一条 room → 下架 → 又发了一条新的 → 现在想恢复旧的。
此时库里我**已经有一条 active 的 room**，恢复会让部分唯一索引当场报错。

两个选择：(a) 自动把当前那条置 `replaced`；(b) **拒绝**，让我自己先下架。

**选 (b)**，理由与裁决 10 完全一致：**(a) 是一次"你没按、但东西被顶掉了"**，
而恢复按钮上写的是"恢复这条"，谁也不会预期它会顺手杀掉另一条。
拒绝的代价是多一步，而这一步只在"下架过、又发过、又想恢复"这个少见的组合里才出现。

## 5. 接口契约（冻结）

### 5.1 读：`GET /api/shares/:kind`（`kind` ∈ `room` | `seed`）

**要求登录**（游客 **401**，不是空列表 —— 空白会让人以为"这里没人分享"）。

```jsonc
{
  "kind": "room",
  "items": [ /* 看板：所有 status='active' 且未过期的行（含我自己那条），created_at DESC, id ASC */ ],
  "mine":  [ /* 我自己所有**未过期**的行（含 hidden），created_at DESC, id ASC */ ],
  "limit": 1,              // 这个 kind 的额度：room 1 / seed 20
  "liveCount": 0,          // ★ 额度用量 = 我自己的行里满足 **status='active' AND expires_at > now** 的条数
  "serverNow": 1757928000000,
  "truncated": false       // 见下
}
```

★ `liveCount` **必须用与看板完全相同的那一个判据**（§4.1），不能只数 `status='active'`：
一条刚过期、还没被回收的行**不占额度**（它已经不在看板上，凭什么占）。
⚠️ 这正是 §3.4 里那个"room 的部分唯一索引不看过期"的另一半 —— 索引与限额的**口径不同**，
而它们必须不同，否则过期未回收的那一小时里你会发不出新的一条。

每一条 item：

```jsonc
{ "id": "…", "kind": "room", "payload": { … }, "note": "1.16 RSG 三缺一",
  "authorName": "某某", "createdAt": 1757928000000, "expiresAt": 1757928600000,
  "status": "active" | "hidden",   // items 里只会是 active；mine 里两种都可能
  "mine": true }
```

- ★ **`serverNow` 是必需的**，不是顺手的。剩余时间必须按服务端时间算：客户端拿它跟本地时钟算一个**偏移量**，
  之后所有倒计时与"到点即从画面消失"都用这个偏移量。只按本地时钟算的话，快 3 分钟的机器会**提前抹掉**还没到点的行，
  慢 3 分钟的机器会让过期的行一直挂着。
- **看板一次最多回 200 行**（`LIMIT 200`）。超出时 `truncated: true`。⚠️ 今天 6 个账号 × 最多 20 条也到不了，
  这个上限是**保险**、不是功能；`truncated` 为真时界面要说一句"只显示了一部分"（不许安静截断）。
- 排序的第二个键 `id ASC` 是**稳定排序**的兜底（本仓每条列表查询都这么做）：同一毫秒写入的两行，
  顺序不能每次都不同 —— 那看起来像"看板在自己变"。
- 响应头 `Cache-Control: no-store`（这是**只给登录用户的管理态数据 + 20 秒一变**，进任何缓存都是错的）。

### 5.2 摘要：`GET /api/shares/summary`

给**公开介绍页**用。要求登录（游客 **401**）。

```jsonc
{ "room": { "live": 3, "limit": 1 }, "seed": { "live": 7, "limit": 20 }, "serverNow": … }
```

⚠️ `live` 是**全站在展示的条数**，不是"我的"。游客拿不到它（那正是"内容不给游客看"的一部分）；
⇒ 介绍页对游客显示「登录后可见」，对登录用户显示「N 条在展示」。

### 5.3 写：`POST /api/shares/:kind`

**要求登录 + 邮箱已验证**（`requireAuth` + `requireVerified`，见 §6.1）。body 按 kind 分叉：

```jsonc
// room
{ "code": "A7K2P", "note": "可选", "minutes": 5 }
// seed
{ "overworld": "1234", "nether": "…", "end": "…", "rng": "…", "note": "可选", "minutes": 10 }
```

| 情况 | 响应 |
|---|---|
| 成功 | **201** `{ "item": { … } }`（回读的服务端那一行，不是"我以为写进去的那一行"） |
| 未登录 | 401 `unauthorized` |
| 登录但邮箱未验证 | **403 `email_not_verified`**（沿用本仓既有拒绝码，前端据此换成"先验证邮箱"那一屏） |
| `minutes` 不在 `{5,10,15,20}` | 400 `invalid_input` |
| 房间号格式/长度不对、种子为空或含空白、说明超预算 | 400 `invalid_input` + `issues`（本仓统一形状） |
| seed 已有 20 条 active | **409 `at_limit`** + `{ "limit": 20 }` |

**语义**：

- `room`：事务内先把我自己所有 **`status='active'`** 的 room 行置 `replaced`，再插新行（§3.4）。
  ⚠️ 注意与 `liveCount` 的口径差别：**替换这一步不看过期**（它要清掉的正是索引挡着的那几行），
  而**额度计数看过期**。两处都要写注释说明为什么不一致，否则下一个人会把它们"统一"掉。
- `seed`：事务内数一遍我自己的行，**判据与 `liveCount` 完全相同**（`status='active' AND expires_at > now`），
  ≥ 20 ⇒ 409；否则**新增一行**（不是替换）。
- `expires_at = created_at + minutes * 60_000`，其中 `created_at` 是**服务端**取的 `now`
  （不接受客户端传时间 —— 那等于让人自己决定什么时候过期）。
- **不校验重复**：同一个房间号可以被两个人同时挂，同一个人也可以把刚下架的那个再挂一次。
  ⇒ 房间号与种子**都不是去重键**，这一条要写进代码注释，免得将来有人拿它做唯一性判断。

### 5.4 下架 / 恢复：`PATCH /api/shares/:id/visibility`

```jsonc
{ "visible": false }   // 下架
{ "visible": true }    // 恢复（只有拥有者）
```

- 与资源那条 `PATCH /api/resources/:id/visibility` **同形**（同一个动词、同一种 body 形状），
  但字段名是 `visible` 而不是 `published` —— `published` 是资源的概念，这里没有"草稿"。
- 权限与非法状态见 §4.2。
- 响应 200 `{ "item": { … } }`（回读）。
- 审计动作见 §6.2。

### 5.5 回收：定时任务

沿用 `index.ts` 里已有的那个形状（启动时跑一次 + 每小时一次 + `.unref()`）：删除 `expires_at < now - 24*3600*1000` 的行。

⚠️ **它的失败只影响库的大小，不影响任何人看到什么** —— 这正是把"到点"做成查询条件换来的性质（§4.1）。
任务里 `try/catch` 并把失败打日志（与 `sweepSessions` 一致：后台任务的失败不该影响服务）。

## 6. 权限与身份

### 6.1 谁能做什么

| 动作 | 要求 | 实现方式 |
|---|---|---|
| 看介绍页 `/shares` | **无**（游客可见） | 不需要接口；两块卡片对游客不显示条数 |
| 看摘要 `GET /api/shares/summary` | 登录 | `requireAuth` |
| 看看板 `GET /api/shares/:kind` | 登录 | `requireAuth` |
| 发布 `POST` | 登录 **+ 邮箱已验证** | `requireAuth` + **已有的 `requireVerified`**（`auth/middleware.ts:126`） |
| 下架自己的 | 登录 + 是这条的 `user_id` | 数据层比对 `user_id` |
| 下架别人的 | `share.moderate` | `requireCapability('share.moderate')` 的**或**关系 |
| 恢复 | **只有本人** | 数据层比对 `user_id`（管理员走到这里一律 403） |

⚠️ **为什么发布这一档复用现成的中间件，而不是挂一个能力**：本仓的 `REQUIRES_VERIFIED` 只对**能力**生效，
而"发一条分享"不是一个能力 —— 它不区分角色（任何验证过邮箱的登录用户都能发）。
正好 `auth/middleware.ts` 里**已经有** `requireVerified`：它返回的就是我们要的那一对
（未登录 401 / 已登录但没验证 **403 `email_not_verified`**），两个码与 §5.3 完全一致。
⇒ 直接 `sharesRoute.post('/:kind', requireAuth, requireVerified, …)` 即可，**不要手写这段判断**。

❌ **也不要**为了"复用 `REQUIRES_VERIFIED`"而新加一个所有角色都有的能力（比如 `share.submit`）：
本仓 `permissions.test.ts` 里那条"没有孤儿能力"的断言挡不住这个 ——
真正的问题是矩阵的每一行都应该回答"**谁能做什么**"，而一条人人皆有的能力回答的是"谁能过验证"。
矩阵一旦开始装这种东西，读它的人就再也无法一眼看完"谁比谁多什么"。

### 6.2 新能力 `share.moderate`

```ts
// packages/shared/src/permissions.ts
CAPABILITIES += 'share.moderate',        // 注释里写明：下架任何人的分享（不可恢复别人的）
EDITOR_CAPS  += 'share.moderate',        // ⇒ editor / admin / owner 都有
```

- 放在 `EDITOR_CAPS` 而不是 `admin` 那一行的理由：**这是内容治理，不是账号治理**。
  与 `resource.moderate`（下架任何资源）同档；本仓的矩阵注释写着「内容治理和账号治理是两条线」。
- ⚠️ 加进 `EDITOR_CAPS` 会让 `admin` 与 `owner` **自动**拥有它（两行都展开 `EDITOR_CAPS`）——
  这是对的，且不会打破"owner 的能力与 admin 完全相同"那条不变量。

**`services/api/src/permissions.test.ts` 的实际后果（现读该文件确认过，不是猜的）**：

- 它**没有**任何"能力总数"之类的写死数字 ⇒ 加一个能力**不会**因为计数而红。
- 三条相关断言**自动成立**：`CAPABILITIES` 里没有"没人拥有"的孤儿能力（`share.moderate` 在 `EDITOR_CAPS` 里）；
  "admin 拥有全部能力"（admin 展开 `EDITOR_CAPS`）；"reviewer 是 user 的超集"（两边都没动）。
- ★ **要动手改一处**：`'★ 普通用户不能审核、不能管账号'` 那一条现在断言了
  `resource.review` / `user.moderate` / `audit.read` 三项为假。**把 `share.moderate` 加进这一组** ——
  这正是"整个权限系统存在的主要理由"那一组里的一员（普通用户能下架别人的分享是越权）。

### 6.3 审计动作（冻结三个名字）

| 动作 | 何时 | `reason` 里必须有的东西 |
|---|---|---|
| `share.create` | 发布成功 | `kind`、展示多少分钟；**room 若替换掉了旧行，写明"替换掉 N 条"** |
| `share.hide` | 下架成功 | **是自己下架还是管理员下架**（沿用资源那条的写法：`（治理者）` / `（作者自己）`） |
| `share.restore` | 恢复成功 | 同上，实际上只有作者自己这一支 |

⚠️ **不给"被替换"单独写一条审计**：它是同一次 `share.create` 的后果，`reason` 里已经写明。
两条记录会让"他发了几次"这个最简单的计数变成要人去重。

## 7. 页面与交互（冻结）

### 7.1 路由与导航

| 路由 | 页面 | 可见性 |
|---|---|---|
| `/shares` | **介绍页** | **公开**（游客可见，不请求任何接口） |
| `/shares/room` | 私人房看板 | 需登录 |
| `/shares/seed` | 种子看板 | 需登录 |
| `/shares/<其它>` | 404 | — |

- `NAV_SECTIONS` 新增一行：`{ to: '/shares', labelKey: 'nav.shares', block: 'shares' }`，
  放在「直播」之后、「排位赛种子」之前（与相邻的"看现在发生什么"类栏目挨着；改顺序就是挪一行）。
- ⚠️ 加这一行会**连带**影响三处，`homerender.tsx` 那一处与我原先的猜测**相反**（现读该脚本确认过）：
  1. **`home.desc.shares` 必须同时加** —— 首页按 `home.desc.<block>` 推每一栏的说明文本；
  2. `homerender.tsx` **没有**写死的栏目条数：它用的是 `NAV_SECTIONS.length`（外加逐栏按 `labelKey` 与
     `home.desc.<block>` 取词条）。⇒ 加一栏**不会**因为"数量对不上"而红，
     **但会因为 `home.desc.shares` 解析不出来而红在那一栏上** —— 也就是说上方第 1 条是它唯一会抓到的东西；
  3. `.sidebar__block--shares` 的 CSS 颜色（左侧那个小方块），照现有六种颜色各来一条的形状加。
- 栏目**对所有人生效**（游客也看得到入口），照 `/me`（账号页）的先例 —— 本仓没有"藏起来的栏目"这种形状。

### 7.2 介绍页 `/shares`（公开）

1. 标题「实时分享」+ 一句导语：**这里分享的东西几分钟后就会自己消失**；**只有登录用户能看到里面的内容**。
2. 两块入口卡片：
   - 「私人房」—— 分享一个房间号让其他人进来
   - 「种子」—— 分享一组世界种子（主世界 / 下界 / 末地 / RNG）
   - 每块卡片：标题 + 一句说明 + 「N 条在展示」（登录用户）或「登录后可见」（游客）+ 整块可点。

⚠️ **游客这一次不请求任何接口**：`GET /api/shares/summary` 要求登录（§5.2），
所以介绍页必须**先看 `useAuth()` 有没有登录再决定发不发那一次请求** —— 不能"发了再吃 401"。
（401 会在服务端留下一条"有人在试着读"的噪音，而且游客看到的闪烁是"先加载再变成登录后可见"。）

⚠️ 游客看到的产物里**不许出现任何一条分享的内容**，也不许出现条数 —— 这条由渲染自检的**产物级断言**守着（§11.2）。

### 7.3 看板页 `/shares/room` 与 `/shares/seed`

从上到下：

| | 内容 |
|---|---|
| 1 | 标题 + 两个标签页（互相切换）+ 一个回到介绍页的链接 |
| 2 | **你的一条**（分叉见下） |
| 3 | **看板**：所有在展示的条目，按发布时间倒序；自己那行带「你」标记 |

**第 2 行按 kind 分叉**：

| | room | seed |
|---|---|---|
| 什么都没挂 | 一句话 + `＋ 挂一条`（展开表单） | 同左，文案是「再加一条」 |
| 有在展示 | 内容摘要 +「还剩 N 分钟」+「下架」+「换一条」 | 「你在展示 3 / 20 条」+ 可折叠列表（每条：摘要 + 剩余 + **各自的「下架」**） |
| 已下架未过期 | 「你下架了这一条」+「恢复」+「挂新的」 | 混在上面那个列表里（每条带「恢复」） |
| 已到 20 条（seed） | — | 发布表单的提交键**禁用**并说明为什么（「你在展示 20 条，先下架一些」） |

**发布表单**：room = `房间号` + `说明（可选）` + `展示时长`（5/10/15/20 四档，**默认 5**）+ 提交键；
seed = `主世界种子`（必填）+ `下界种子` / `末地种子` / `RNG 种子`（选填）+ `说明（可选）` + `展示时长` + 提交键。

**四个键的文案要说清是哪一件事（别用同一个词）**：

| 位置 | room | seed |
|---|---|---|
| 展开表格的按钮（没有在展示时） | `shares.formOpenRoom`「挂一条」 | `shares.formOpenSeed`「挂一条」 |
| 展开表格的按钮（有在展示时） | `shares.formOpenRoomAgain`「换一条」 | `shares.formOpenSeedAgain`「再加一条」 |
| 表单里的提交键（没有在展示时） | `shares.formSubmitRoom`「发到看板」 | `shares.formSubmitSeed`「加进看板」 |
| 表单里的提交键（有在展示时） | `shares.formReplaceRoom`「发到看板（替换你正在展示的那条）」 | 同上（seed 不替换，两处一样） |

- ⚠️ room 的提交键在**有在展示**时必须是"替换"那一句（§7.3 最后那条注）。
- ⚠️ **下架不做二次确认**：它是可逆的（有「恢复」），本仓对可逆动作不加确认框。
  反过来，**替换是"旧的再也回不来"**，所以那句文案必须写在按钮上（而不是藏在 tooltip 里）。
- ⚠️ 房间号与种子的输入值**两端空白先 trim**（`" A7K2P "` ⇒ `A7K2P`），
  **中间**的空白按 §3.2 的字符集判（房间号含空格 = 非法；种子含空白 = 非法）。trim 之后就**原样保存原样显示**，
  不折叠大小写、不做任何归一化。

### 7.4 看板每一行长什么样

`内容` → `说明`（空则整行不渲染）→ `谁发的` → `还剩 N 分钟`。

- room：房间号**放大显示** —— 用**现成的 `--fs-title-item` 档（18px）** + 中等字重，
  ⚠️ **不新造字号**：像素字体只在 12 / 18 / 24 / 30 清晰（`styles.css` 末尾那一块是口径的唯一出处）。
- seed：**只显示填了的那几格**，各带标签（主世界 / 下界 / 末地 / RNG）；空的格子不渲染，
  **不显示成一排破折号**（那看起来像"这里本来该有东西，丢了"）。
- 剩余时间：`还剩 N 分钟`；最后一分钟 `不到 1 分钟`。★ "到点那一秒从画面上消失"由**本地计时**负责，
  所以分钟粒度不会撒谎（它不会显示"还剩 0 分钟"）。
- ★ **「复制」按钮**：房间号一个、种子的每个值各一个，**每一行都有** ——
  复制是给**看的人**用的（他要把别人的房间号拷进游戏），不是只给作者用的。
  实现用 `navigator.clipboard.writeText`；失败时给一句看得见的提示（**不许静默**）——
  剪贴板 API 在非 HTTPS 或没有权限时会 reject。

### 7.5 四种整体画面（都要有，且必须能被断言）

| 画面 | 内容 |
|---|---|
| **游客**（看板页） | 一句"登录之后才能看这里分享的东西 —— 它们只在登录用户之间可见" + 登录入口。**不请求接口。** |
| **登录但邮箱未验证** | 看板照常；第 2 行换成"要挂东西得先验证邮箱" + 一个**重发验证邮件**的入口（复用已有的 `POST /api/auth/verify/resend`） |
| **正常** | 上面那套 |
| **接口挂了** | **保留上一次的列表** + 一句「上次刷新失败了，下面是 N 秒前的数据」+ 重试。⚠️ **绝不清空** |

### 7.6 自动刷新

- 每 **20 秒**重新拉一次 `GET /api/shares/:kind`。
- **页面不可见时停止**（`document.visibilityState`），回到前台立刻刷一次。
  ⚠️ 不加这一条，一个挂在后台的标签页会一直打服务器 —— 而这是个 1 核服务器。
- **本地**计时：每秒用 `serverNow` 偏移量重算剩余时间，到点的行**当场从画面移除**（纯本地，不发请求）。
- 刷新失败**不清空**旧列表（§7.5 第 4 行）。
- 界面上的"最后更新时间"用**相对秒数**（`shares.updatedAgo`「{{secs}} 秒前更新」），它自己也随本地计时走。
- ⚠️ **介绍页 `/shares` 不自动刷新**：它是静态介绍 + 一个附注性质的条数，没有"实时"的要求。
  这一条要写出来，否则实现者会因为"同属一个栏目"而顺手给它也加一个定时器。

## 9. 这次明确不做（逐条给理由）

| 不做 | 理由 |
|---|---|
| **不给游客看内容** | 用户明确要求。⚠️ 这是全站第一条这样的线，见 §1.1 |
| 不做评论 / 点赞 / 举报 | 20 分钟的东西挂评论没有意义；举报是"内容永久留下"才需要的机制 |
| 不做历史记录页（"谁以前分享过什么"） | 行 24 小时后就被删了，一个能查历史的页面与"短暂"这个前提冲突 |
| 不做"谁看过" | 需要按人记浏览，与"只有登录用户可见"叠加会立刻变成一份用户行为记录 |
| 不做私聊 / 邀请 | 这是另一件事（而且本仓没有消息系统） |
| 不给 `live_shares` 做全文搜索 | 内容是 20 分钟一换的；搜索一个正在消失的东西没有意义 |
| 不做"续期 / 延长展示" | 用户没要求；重新发一条就是替换/新增，语义已经够了 |
| 不做编辑已有条目 | 同上：改内容 = 下架 + 重发。⚠️ 这样也让"条目内容不可变"成为一条可以依赖的性质 |
| 不做桌面端专门界面 | 沿用网页（桌面端就是加载同一个站点） |
| 不给这一栏加限流 | 用户明确裁决（§2 裁决 4） |
| 不做"到期前 N 分钟提醒作者" | 需要通知渠道；而且作者就挂在页面上，剩余时间是常显的 |
| **不看板不分页**（只设 200 行硬上限） | 今天 6 个账号；分页会让"到点消失"和翻页打架。⚠️ 上限存在且 `truncated` 可见 |

## 10. 边界与已知限制（实现者与评审都要知道）

1. **`payload` 的形状只有应用层知道。** 数据库不知道"room 必须有 code"。缓解：写入与读出**过同一份 zod**；
   形状对不上的行**跳过并记日志**，有一条测试喂这种行（§11.1）。这是选"一张表 + JSON"换来的代价，不是遗漏。
2. **seed 的 20 条额度不是数据库强制的**（只有一条测试）。理由与取舍见 §3.3。
3. **回收任务每小时跑一次**，所以库里最多可能留 25 小时的行。它只影响体积。（`ls` 看到的 `mcsr.db` mtime
   在 WAL 模式下会滞后，别用文件时间判断"任务跑没跑"，要查库。）
4. **种子不允许含空白字符**（用户批准的口径 3）。⇒ 一个带空格的文本种子会被拒。按 MCSR 的实际用法
   （种子是数字或连续字符串）这是可接受的；如果将来真的出现了带空格的种子，改的是一处正则 + 一条测试。
5. **房间号不做唯一性判断**：同一个码可以被两个人同时挂（现实里就是两个人抄了同一个房）。
6. **本栏目对游客关闭** —— 见 §1.1。
7. **无审核**。全部兜底只有四条：只有登录用户可见、room 一人一行、最多 20 分钟后消失、管理员可下架（裁决 11）。
8. **没有"暂停 / 冻结"**：下架与过期是仅有的两种下线方式。
